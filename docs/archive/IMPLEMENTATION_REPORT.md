# Afrinov Platform — Implementation Report

**Status:** Production prototype  
**Scope:** Bounded-context foundation + Inventory + Procurement + Reporting + Identity & Access (per ADR-001).

---

## A. Understanding

The system replaces a family of error-prone `.xlsm` spreadsheets used by Afrinov to track inventory and project consumption. The documented spec (in `../afrinov-docs/docs/`) models the system as a **modular monolith** with bounded contexts (Identity & Access, Procurement, Inventory, Operations, Reporting, Document Management), implements **stock as an immutable transaction ledger** (ADR-002), normalises **locations** (ADR-003), and unifies the **five existing material categories** under one `Material` schema (ADR-004). This implementation covers the foundation plus the three priority contexts (Inventory, Procurement, Identity & Access) and the read-only Reporting context; Operations and Document Management are intentionally deferred (see §L).

## C. Architecture decisions

- **Modular monolith, TypeScript end-to-end.** Single language, single deployable, internal module boundaries enforce bounded contexts.
- **Fastify over Express.** Schema-validated routes, lower overhead, built-in pino logger.
- **Prisma.** Strong typing for the data model; migrations + `prisma migrate deploy` for production.
- **JWT auth (HS256).** Simpler than sessions for an SPA + API at this scale; rotate via env.
- **Permission codes are data, not enums.** Stored in `permissions` table, mapped to roles in `role_permissions` — admin can grant/revoke without code changes.
- **Decimal arithmetic everywhere.** No `number` for quantities (ADR-002 invariant).
- **Domain events are in-process.** ADR-001 explicitly rejects a broker at this scale.
- **Materialised balance table kept in sync synchronously.** Each mutation is in one Prisma transaction; the balance row for the affected `(material, location)` is recomputed before commit. This trades a little write throughput for read speed and a very small blast radius — exactly the trade-off appropriate for Afrinov's scale.

## D. Database

Tables: `users`, `roles`, `permissions`, `user_roles`, `role_permissions`, `materials`, `locations`, `suppliers`, `projects`, `purchase_orders`, `purchase_order_lines`, `goods_receipts`, `goods_receipt_lines`, `inventory_transactions`, `inventory_balances`, `audit_log_entries`. All enums map to the values in `03-domain/entity-catalog.md` (Pascal-cased in Prisma, kebab/camel-cased in API responses).

Critical constraints:
- `inventory_transactions` is append-only by application convention; no UPDATE/DELETE in service code.
- `inventory_balances` is upserted only by `recomputeBalance(...)`, which itself sums transactions — never accepts a quantity from outside the transaction.
- FKs cascade appropriately (e.g. `purchase_order_lines` cascade on PO delete when in DRAFT).
- Indexes on `(material_id, location_id, posted_at)`, `reference_type, reference_id`, `status` on PO/GR, and `category` on materials.

Migrations are managed by Prisma (`prisma migrate dev` / `prisma migrate deploy`). Initial migration will be generated by the operator via `npx prisma migrate dev --name init`.

## F. Frontend

SPA, route-based navigation, JWT in `localStorage`, all forms Zod-validated on the server. Pages implement: dashboard, materials list, current-stock report, movement history, issue/transfer/adjust forms, suppliers, PO creation + submit, goods receipt create + post, low-stock report. Loading, error, and empty states are present on every list page. Accessibility: semantic HTML, labelled inputs, role="alert" / role="status" on messages.

## G. Business logic implemented

- FR-INV-001…008 (material master, receipts/issues/transfers/adjustments, derived balance, threshold flag, tool-category modelling).
- FR-PROC-001…004 (supplier master with case/whitespace-insensitive uniqueness, PO creation with lines, PO-linked receipts, ad-hoc receipts).
- FR-REP-001…004 (current stock, movement history, low stock, project consumption).
- FR-SEC-001…003 (JWT auth on every business endpoint, role-based permission checks via `requirePermission`, audit log on every material/supplier/user mutation and PO transition).

PO state machine respects the documented transitions (see `procurement.service.ts`). GoodsReceipt posting atomically creates Receipt transactions, updates PO received quantities, and recalculates the PO status to PARTIALLY_RECEIVED / FULLY_RECEIVED.

## H. Security controls

- All mutating routes go through `requirePermission(...)` after JWT verification (`server.ts` authenticate preHandler).
- Passwords hashed with bcrypt (cost 10).
- Server-side Zod validation on every request body; never trust client types.
- Adjustments, issues, and transfers are server-side re-validated against current balance (`INSUFFICIENT_BALANCE` error).
- `audit_log_entries` records actor + before/after for material, supplier, user, and PO transitions.
- Secrets only in `.env`, never in source. `.env.example` is committed; `.env` is gitignored.

## L. Known limitations

- **Excel → DB migration script is not included.** Schema can ingest the data; building the importer + cleansing map is a separate workstream.
- **Operations** (Projects CRUD) and **Document Management** bounded contexts are out of scope for this prototype.
- **Tool check-out/check-in** state machine UI is not built. The model supports it; the UI is deferred.
- **i18n, multi-currency, batch/serial tracking, multi-warehouse** are explicitly not adopted per `05-sap-study/sap-not-to-copy.md`.
- **Rate limiting, request tracing, metrics** are deployment-layer concerns; not implemented in code but the server emits structured logs that an OTel collector can scrape.

## M. Risks

- **Permission codes are free-text strings.** A typo at seed time creates a code that no role references. Mitigated by `permissions.test.ts` and by always seeding via `db/seed.ts`.
- **In-process events can swallow handler exceptions.** Today `dispatchDomainEvents` lets one handler's rejection abort the rest. For v1 this is fine (handlers are idempotent recaulculations); if more consumers are added, switch to a queue.
- **Concurrent receipt posting against the same PO.** Each GoodsReceipt is independent; two parallel posts against the same PO can both set status to FULLY_RECEIVED. The DB-level unique constraint on `po_lines.id` and the increment-update on `receivedQty` is safe; the only race is the final status comparison, which is best-effort and recovers on the next post.
- **Single JWT secret.** Acceptable for v1; rotate before production. Plan a JWKS / refresh-token flow if multi-service emerges.
- **Inventory service tests are unit-level, not DB-backed.** They exercise the service through a mocked Prisma transaction. End-to-end behaviour against PostgreSQL is not asserted by automated tests in this prototype — recommended to add a CI job that boots Postgres and runs the same assertions against the real client before any production deployment.
