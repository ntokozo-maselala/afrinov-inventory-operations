A fresh disposable PostgreSQL 16 database on loopback port 5434 applied all 23 existing migrations successfully; after the documented test-only seed prerequisite was supplied, the unchanged integration suite passed 15 files / 99 tests. WP2 uses transaction-scoped PostgreSQL advisory locks in stable `(materialId, locationId)` order across all application ledger writers. This preserves the ledger as the source of truth while serializing balance validation and recomputation. The lock helper relies on PostgreSQL and is intentionally exercised only by the real integration seam; unit tests mock it as an isolated boundary. Migration risk: none (no schema change). Security implication: the lock keys contain only internal identifiers and neither secrets nor customer data are logged. WP3 adds no schema migration and no new dependency. The transaction claim and PO-line advisory lock are PostgreSQL-specific but remain internal; they serialize only the affected receipt/PO-line work and preserve the append-only ledger/API behavior. A failed post rolls back the claim, ledger rows, PO quantities and status changes with the surrounding Prisma transaction. WP4 changed only report query validation, backend dependency manifests/lockfile, the affected OpenAPI type annotation, and inventory-route UUID compatibility required by the Zod 4 major upgrade. The report arrays accept at most 100 values each; accepted filters and OpenAPI generation remain compatible.
